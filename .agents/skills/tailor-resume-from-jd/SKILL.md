# 职位定向简历优化

将初始简历视为不可变的视觉基准，将个人主页视为补充事实来源，将新 JD 视为内容筛选、篇幅分配和要点强调依据。除非用户明确要求，否则不要改动初始简历、个人主页或其公开 PDF；在独立交付目录生成新的 HTML 和 PDF。

开始前完整阅读 [references/template-contract.md](references/template-contract.md)，并按其中的版式合同执行。若当前仓库是 `zlr930.github.io`，同时阅读 [references/current-template-profile.md](references/current-template-profile.md)；先核对其中的样式哈希，哈希不一致时以仓库当前源文件为准并重新实测。

## 输入识别

1. 定位用户指定的初始简历、个人主页和 JD。优先使用用户明确给出的文件或 URL。
2. 若工作区是本技能的示例站点，按版式合同列出的已知路径检查；不要假设其他仓库也有同样结构。
3. 若存在多份简历，将用户称为“初始简历”“原简历”或当前主页展示的版本作为视觉基准；无法可靠判断时才询问。
4. 提取可核验事实：单位、职位、时间、职责、项目、工具、数据、成果、教育经历和校园经历。不得补写来源中不存在的经历、技能或数字。

## 建立岗位映射

先在内部建立“JD 要求 → 已有证据 → 使用位置”的映射，再写简历：

- 将职责和要求拆成硬技能、业务流程、工具、成果、行为特质和加分项。
- 优先选择有具体行动、工具、协作对象、数量或结果支撑的经历。
- 用岗位语言重述已有事实，但不改变事实边界。例如可将“跟进交付”表述为“跟踪交付节点”，不能凭空增加招标、谈判或合同经验。
- 对没有证据的要求保持空缺，不用自我评价替代事实。
- 保留用户明确要求必须出现的经历；内容过多时，先删减低相关项目或校园条目，再压缩低相关经历。

## 编写内容

1. 保持原简历的栏目体系、条目结构和日期样式，除非用户明确要求调整。
2. 项目经历先遵循用户或当前模板档案确认的分组优先级，再在每组内按时间倒序排列。当前示例站点必须将全部竞赛经历置于全部 AI 个人实践之前；竞赛组和 AI 个人实践组内部均从最近到更早排列，同月项目保持来源中的相对顺序。JD 相关性只用于决定内容取舍、篇幅和强调，不得打乱该分组与组内时间顺序。
3. 项目日期必须复用用户或事实来源确认的起止时间，不得把已结束项目写成“至今”。当前示例站点的“AI Agent 驱动的自媒体运营与 SOP 自动化”时间固定为“2026.02 — 2026.03”；除非用户提供更新事实，不得改写为其他时间。
4. 每条经历优先写成“职责/场景 + 行动/方法 + 工具/协同 + 结果”。保留来源中的量化数据。
5. 对高相关经历给足信息密度；低相关经历可减少要点，但不要把用户指定保留的关键经历写成一句空泛概括。
6. 项目过多时可合并同类个人实践，但保留每个实践的真实名称、核心动作或成果，使其仍可核验；合并后先归入对应分组，再按合并条目覆盖的最近时间参与组内倒序排列。
7. 自我评价只保留有经历支撑且与 JD 相关的能力。
8. 标题、表头、联系方式和技能标签默认完全沿用初始简历。只有用户明确要求时才改动。

## 复用视觉模板

1. 先检查初始简历的 HTML/CSS/组件或 PDF，记录页面尺寸、DOM 层级、字体栈、字号、字重、行高、字距、颜色、边距、间距、图标和加粗方式。
2. 若有源代码，复用同一 DOM 结构和同一份样式表；独立交付必须复制样式时保持文件内容逐字节一致。不要新增或覆盖 CSS，不要重新设计布局，不要改成双栏或新增求职方向。
3. 若只有 PDF，先用 PDF 渲染图和字体信息建立视觉基准，再以最少结构重建。无法确认字体文件时明确说明风险，不要声称像素一致。
4. 新简历应是独立产物。默认输出到 `deliverables/` 或仓库既有的交付目录，使用岗位安全的文件名。
5. 加粗必须复用原模板的标签和 CSS 类。只加粗与岗位直接相关的职责、方法、工具、成果或关键身份；不要整句、整段或密集加粗。
6. 深色标题方块、图标和装饰元素必须与原模板一致，且不得擅自在纯装饰方块中加入文字。

## 调整为一页

按内容优先级逐步调整，禁止用明显缩小全局字体、压扁行高或改变页边距来强行塞入：

1. 删除重复表达和低价值自我评价。
2. 合并同类个人项目或实践。
3. 减少低相关条目的要点数量。
4. 缩短或改写低优先级文字，直到内容适配原模板；不得通过修改字体、字号、字重、行高、页边距或区块间距适配页面。
5. 页面必须视觉上铺满一整页，同时保留合理安全底边；不能只满足“不溢出”就交付，也不能让页面下半部出现明显大片空白。优先恢复来源中与岗位相关的真实实习、项目或其他经历来填充内容，不得用改 CSS、放大空白或虚构经历填充。候选页底部留白应以原模板实测值为基准，原则上控制在约 20–60px（或基准值上下 10px）内，不得截断、重叠、跨页或出现第二页。

## 验收与导出

在交付前完成以下检查：

1. 运行项目已有的构建、类型检查或 lint，范围与改动相称。
2. 使用浏览器分别打开初始简历和候选简历，等待字体和图片加载完成。
3. 使用 [scripts/validate_resume.mjs](scripts/validate_resume.mjs) 比较字体属性、浏览器实际采用的字体、表头文本及像素、图片加载、单页尺寸、溢出和页面填充，并导出 PDF。底部填充校验不能直接沿用宽松默认值，应先测量基准页，再通过 `--min-bottom-px` 与 `--max-bottom-px` 将候选页控制在基准值附近；只有原模板本身明显留白时才放宽范围。Linux 无头浏览器缺少原模板中文字体时使用 `--normalize-cjk-fonts`，禁止把字体回退后的 PDF 当作正式交付。
4. 用 `pdfinfo` 或 `file` 再确认 PDF 恰好一页；必要时渲染为图片目检全文、底部边距、加粗和重叠。
5. 检查初始简历和个人主页文件没有被改动。若仓库使用 Git，查看相关文件的 `git diff`，不要回退用户原有改动。

示例命令：

```bash
node .agents/skills/tailor-resume-from-jd/scripts/validate_resume.mjs \
  --baseline-url http://127.0.0.1:5173/resume/ \
  --candidate-url http://127.0.0.1:5173/deliverables/target-resume.html \
  --output-pdf deliverables/target-resume.pdf \
  --screenshot deliverables/target-resume.png
```

在 macOS 或 Windows 上优先使用本机模板字体直接导出；仅当实际字体检查报告回退且无法换到具备模板字体的系统时，才附加 `--normalize-cjk-fonts`。若表头经用户授权发生变化，附加 `--allow-header-change`。若原模板本身不是接近满页，才使用 `--skip-fill-check`，并在交付说明中注明。

## 交付说明

简要说明生成的 HTML/PDF 路径、针对 JD 的主要内容调整、验证结果，以及任何无法确认的字体或来源限制。不要只交付文案而不生成 PDF，除非用户明确只要文本。
